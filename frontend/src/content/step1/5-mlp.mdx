## MLP.hpp

Good news: this is the short one. All the hard thinking happened in ```layer.hpp```, and a multilayer perceptron is a
list of layers with a rule for walking it forwards and a rule for walking it backwards. If ```layer.hpp``` made sense
then this file is mostly bookkeeping.

Imports.

```cpp
#pragma once
#include <iostream>
#include <vector>
#include <stdexcept>
#include <random>
#include "matrix.hpp"
#include "layer.hpp"
#include "math.hpp"
```

The attributes are three vectors.

```cpp
struct MLP{
    std::vector<int> layer_sizes;
    std::vector<Activation> activations;
    std::vector<Layer> layers;
```

```layer_sizes``` describes the shape of the whole network as a list of widths, and ```layers``` is the actual stack.
```activations``` holds one enum per layer. Notice that ```layer_sizes``` has one more entry than the other two, and that
offset is the thing to get straight before you read the constructor. Widths are the boundaries between layers, and layers
are the gaps between the boundaries, so $n$ widths give $n - 1$ layers. The comment in the source says it best.

```cpp
    /*  
        layer_sizes: e.g. {2, 4, 1} = 2 inputs -> 4 hidden -> 1 output.
        activations: one per layer (size == layer_sizes.size() - 1), so
        activations[i] is the activation applied by the layer mapping
        layer_sizes[i] -> layer_sizes[i+1].
    */
```

Now the constructor, which is mostly three guards.

```cpp
    MLP(const std::vector<int>& l_sizes, const std::vector<Activation>& acts, std::mt19937& rng)
        : layer_sizes(l_sizes), activations(acts) {

        if (layer_sizes.size() < 2){
            throw std::invalid_argument("MLP needs at least an input and an output size");
        }
        if (activations.size() != layer_sizes.size() - 1){
            throw std::invalid_argument("activations must have one entry per layer (layer_sizes.size() - 1)");
        }
        // train() applies softmax + cross-entropy itself, so the output layer
        // must hand back raw logits -- LINEAR is the only activation that does.
        if (activations.back() != LINEAR){
            throw std::invalid_argument("output layer activation must be LINEAR (train() applies softmax+CE itself)");
        }

        layers.reserve(activations.size()); //this is optimisation - makes things faster. 
        for (std::size_t i = 0; i < activations.size(); ++i){
            layers.emplace_back(layer_sizes[i], layer_sizes[i + 1], activations[i], rng);
        }
    }
```

The first two guards are the offset we just talked about, enforced. The third one is the interesting one, and it is the
payoff for a promise made two pages ago. Softmax and cross-entropy are a matched pair, and the fused gradient
$(p - y)/N$ from the <LearnLink to="/training/step1/learn/math">math page</LearnLink> is only the right answer when the
thing being softmaxed is raw logits. Put a $\tanh$ on the output layer and every number the loss sees has already been
squashed into $(-1, 1)$, the fused gradient quietly becomes the wrong gradient, and the model still trains, just badly,
with nothing anywhere telling you why. So the constructor refuses. It is a nice example of turning a subtle maths bug
into a loud error at construction time, which is generally the best trade you can make.

```reserve``` is worth a word too. Growing a ```std::vector``` means allocating a bigger block and moving everything
across, and every ```Layer``` in here owns six matrices, so a regrow means shuffling all of that around. Telling the
vector up front exactly how many layers are coming means it allocates once and never moves them.

Now the forward pass over the whole stack.

```cpp
    const Matrix& forward(const Matrix& input) {
        const Matrix* current = &input; //current is the pointer to a matrix which is the reference of input

        for (auto& layer : layers) {
            current = &layer.forward(*current);
        }

        return *current;
    }
```

Three lines, and the pointer is the whole point. ```Layer::forward``` returns a ```const Matrix&``` into the layer's own
```cache_output```, so what we keep here is the address of that buffer, and we hand it straight to the next layer. Write
it with a ```Matrix current = ...``` instead and you would copy the entire batch of activations at every single layer,
for no reason at all. A pointer is the natural way to say "whichever matrix we are currently looking at" when you have no
intention of owning it.

Backward is the same walk in reverse.

```cpp
    Matrix backward(const Matrix& loss_grad){
        Matrix current = loss_grad;
        for (auto it = layers.rbegin(); it != layers.rend(); ++it){ //iterator using a pointer, start at RHS and go Left
            current = it->backward(current);
        }
        return current;
    }
```

```rbegin``` and ```rend``` are the reverse iterators, so this starts at the last layer and works towards the first,
which is the only order that can work: a layer cannot know its own gradient until the layer in front of it has produced
one. Here ```current``` is a real ```Matrix``` rather than a pointer, because ```Layer::backward``` builds a fresh matrix
and returns it by value, so there is nothing on the layer to point at.

The value that falls out of the end is $\partial L / \partial X$ for the very first layer, which is the gradient of the
loss with respect to the input data itself. Nothing in Step1 uses it, since we cannot change MNIST. It is genuinely
useful elsewhere though, and this is the quantity that adversarial examples are built out of, so it is nice that the
function hands it over rather than dropping it.

Last comes ```train```, and I want to flag something about it before you read it.

```cpp
    void train(const Matrix& X, const Matrix& truth, int epochs, double lr){
        for (int epoch = 0; epoch < epochs; ++epoch){
            const Matrix& prediction = forward(X);
            Matrix probs = prediction;   // copy: softmax mutates in place, prediction is const&
            softmax(probs);
            Matrix loss_grad = cross_entropy_loss_grad(probs, truth);
            backward(loss_grad);
            for (auto& layer : layers){
                layer.update(lr);
            }
            if (epoch % 100 == 0){
                double loss = cross_entropy_loss(probs, truth);
                std::cout << "epoch " << epoch << " loss " << loss << "\n";
        }
        }
    }
```

Read it as the definition of an epoch and it is perfect. Push the whole dataset forward, softmax the logits into
probabilities, get the fused gradient, push that backward, nudge every layer downhill, occasionally say something. Five
steps, and that is genuinely all training is.

The flag is this: the driver in ```main.cpp``` never calls it. It writes its own loop instead, because it wants to
shuffle the data and cut it into mini-batches, and doing that from inside ```MLP``` would mean this struct knowing about
batch sizes and random number generators and sample ordering, none of which is really its business. So ```train``` here
is the honest reference version, the one you would write first and the one that shows the shape of the thing, and the
driver is the version with the practical bits bolted on. We will look at those on the next page. If you are reading the
source alongside this and wondering why changing ```train``` has no effect on your accuracy, thats why.

One last thing worth mentioning, even though it does not get a page of its own. There is a ```grad_check.hpp``` next to
these files, and it is the answer to a question you should be asking by now, which is how anyone knows the backward pass
is right. All those transposes and Hadamard products could be subtly wrong and training would still sort of work. The
check is delightfully simple. Nudge one weight by a tiny $\varepsilon$, measure how much the loss actually moved, divide,
and you have an approximation of that weight's derivative that owes nothing to our algebra. Then compare it against what
```backward``` claims:

$$
\frac{\partial L}{\partial w} \approx \frac{L(w + \varepsilon) - L(w - \varepsilon)}{2\varepsilon}
$$

Run ```nn --dataset xor --grad-check``` and it does this twice, once on a ```LINEAR``` layer with softmax and
cross-entropy, and once on a ```TANH``` layer with mean squared error. Two checks rather than one, because the
```LINEAR``` case never multiplies by an activation derivative, so on its own it would leave the entire $f'(a)$ and
Hadamard path in ```Layer::backward``` untested.

That is ```MLP.hpp``` done: a constructor with three opinions, a forward walk, a backward walk, and a training loop. Now
lets go and find something to train it on.
