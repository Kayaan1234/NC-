## math.hpp

We firstly revisit some activation functions. The non-linearities, as mentioned before, are very important, as without them
a multi-layered network would simply condense into a linear model. It is worth seeing exactly why, in one line. Stack two
linear layers with no activation between them and you get

$$
W_2(W_1 x + b_1) + b_2 = (W_2 W_1)\,x + (W_2 b_1 + b_2)
$$

which is one weight matrix and one bias vector: a single layer wearing a costume. Ten layers collapse the same way. The
function squeezed between them is the only thing that depth actually buys you.

Imports first:

```cpp
#pragma once
#include <cmath>
#include <vector>
#include <algorithm>
#include <stdexcept>
#include "matrix.hpp"
```

```matrix.hpp``` is in that list because this file works at two different scales. The activations are scalar. We have one
```double``` in, one ```double``` out and each get handed to ```apply_``` from the
<LearnLink to="/training/step1/learn/matrix">matrix page</LearnLink> to be run over every cell. The losses cannot work that
way: a loss has to see a whole batch at once in order to average over it, so those take ```Matrix``` arguments.

And lets revisit the already seen activation function.

```cpp
inline double sigmoid(double x){
    return (1.0/(1.0+std::exp(-x)));
}
inline double sigmoid_deriv(double a){
    return a * (1.0 - a);
}
```

Nothing there has changed since the <LearnLink to="/training/step0/learn/math">single neuron's math.hpp</LearnLink>, but one
detail deserves a little bit of a stop, because it is the convention that **every** derivative on this page follows.

Look at the parameter name. It is ```a```, not ```x```, and that is not decoration. The derivative of the sigmoid is
usually written in terms of its input $z$, but it can be rewritten in terms of its own output $a = \sigma(z)$:

$$
\sigma'(z) = \sigma(z)\bigl(1 - \sigma(z)\bigr) = a\,(1 - a)
$$

The forward pass has already computed and stored that $a$, so the backward pass gets its gradient from one multiply and one
subtract, with no ```std::exp``` anywhere. The expensive part was paid on the way forward and is simply reused on the way
back.

The trap is that $z$ and $a$ are both a plain ```double```. Passing the pre-activation where the output is expected
compiles cleanly, runs at full speed, and hands back a wrong number. For the rest of this file, read a parameter named ```a``` as *the
value that came out*, never *the value that went in*.

Now lets look at some new nonlinearities. I will introduce them alongside their derivatives as well.

```cpp
inline double tanh_act(double x){
    return std::tanh(x);   // overflow-safe; avoids clashing with C's ::tanh
}

inline double tanh_deriv(double a){
    return 1.0 - a * a;
}
```

$\tanh$, or as I like to call it, _tan-sh_, is a hyperbolic function defined as

$$
\tanh(x) = \frac{e^{x} - e^{-x}}{e^{x} + e^{-x}} = \frac{e^{2x} - 1}{e^{2x} + 1}
$$

The value of the function for any $x$ is bounded by $-1$ and $1$. $\tanh$ is also zero-centred (it passes through the
origin) so a layer's outputs are spread either side of zero rather than being uniformly positive the way sigmoid's are.
Like sigmoid, $\tanh'(x)$ can be computed straight from the output of $\tanh(x)$, and the quotient rule shows why. Write
$u = e^{x} - e^{-x}$ and $v = e^{x} + e^{-x}$, and notice that differentiating either one gives you the other: $u' = v$
and $v' = u$.

$$
\tanh'(x) = \frac{u'v - uv'}{v^{2}} = \frac{v^{2} - u^{2}}{v^{2}} = 1 - \left(\frac{u}{v}\right)^{2} = 1 - \tanh^{2}(x)
$$

So with $a = \tanh(z)$ cached from the forward pass, the whole derivative is ```1.0 - a * a```. Note the function's name
as well: ```tanh_act```, not ```tanh```. ```<cmath>``` brings C's ```::tanh``` into scope, so a function of our own with
that name and the same ```double``` signature collides with the one that is already there rather than sitting beside it as
an overload. Naming around the clash is far cheaper than fighting it.

That comparison is the reason why we use $\tanh$ over sigmoid in a hidden layer, and also the reason it is not
enough on its own. Backprop multiplies one activation derivative into the gradient for every layer it travels back
through. Sigmoid's derivative peaks at $0.25$, so four sigmoid layers multiply a gradient by at most
$0.25^{4} \approx 0.004$. This is a 256-fold shrink in the *best* case, before the earliest weights see anything at all. $\tanh$'s derivative peaks at $1.0$, four times
better, and a unit sitting near the origin passes its gradient back essentially intact. But *peak* is the operative word:
that maximum is only reached at $z = 0$, and out in the tails where $\lvert a \rvert$ approaches 1, $1 - a^{2}$ approaches
zero just as surely as sigmoid's does. Let the units saturate, which growing weights will do, and the early layers stop
learning again. $\tanh$ moves the vanishing gradient problem but it does not remove it. That motivates the next activation
function.

Rectified linear unit, or ```ReLU```, is the simplest of the three and also the most common choice in hidden layers. It is
remarkably easy to understand: if $z$ is positive we output $z$, and if $z$ is negative or zero we output $0$. No
exponentials anywhere, just one comparison.

$$
\mathrm{relu}(z) = \max(0, z)
\qquad
\mathrm{relu}'(z) = \begin{cases} 1 & z > 0 \\ 0 & z \le 0 \end{cases}
$$

```cpp
inline double relu(double x){
    return std::max(0.0,x);
}
inline double relu_deriv(double a){
    // relu(z) > 0  iff  z > 0, so the output a carries the same sign info.
    // Undefined at 0 mathematically; like most libraries we use 0.
    return (a > 0.0) ? 1.0 : 0.0;
}
```

The take-the-output convention survives here for a slightly different reason than it does for the other two. There is no
identity rewriting $\mathrm{relu}'$ in terms of $a$; it is simply that ReLU preserves the one fact the derivative needs.
The output is positive exactly when the input was, so testing $a$ answers the same question as testing $z$ would.

Strictly, the derivative does not exist at $z = 0$: the slope coming in from the left is 0, the slope going out to the
right is 1, and there is no single tangent at the corner. The code returns 0 there, which is what most libraries do. A
pre-activation landing exactly on 0.0 is an event no real training run ever notices.

There are some slight variations on this activation function, and it is that flat half they all attack. Because
$\mathrm{relu}'(z) = 0$ for every $z \le 0$, a unit whose pre-activation is negative for every sample in the dataset
receives exactly zero gradient, forever, and it cannot recover, because the update that would move it is itself multiplied by
that zero. That is a **dead ReLU**. To name two of the variations: Leaky ReLU replaces the flat half with a shallow slope,
usually $0.01z$, so a negative unit still receives something; ELU, the *exponential linear unit*, uses $\alpha(e^{z} - 1)$
below zero instead, which is smooth at the origin and levels off at $-\alpha$ rather than diving. Neither ships in this
file. ReLU is what Step1 uses but I think the names are worth knowing, and now so is the problem they were invented to solve.

Next function is a challenging one, so I think its appropriate to explain in _somewhat_ simple English. Imagine at the
final layer, you have a bunch of raw numbers that are difficult to interpret. Some are high, some are low, some are even
negative. Those raw scores have a name — **logits** — and your job is to turn each one into the probability your model
assigns to that option being the true label. Thats where softmax comes in. Softmax goes into your output cells, and
elegantly transforms them into numbers between 0 and 1, and ensures all numbers in that particular output vector sum to
1.0, thus giving you a probability distribution.

$$
\mathrm{softmax}(z)_j = \frac{e^{z_j}}{\sum_{k=1}^{C} e^{z_k}}
$$

The function in this file is a numerically stable version of that, and the outputs are identical. You firstly translate
every value in the row by subtracting the largest value in that row. Then for each of these new values, raise $e$ to the
power of it, which makes every one of them positive. Then divide each through by the total of all of them, to get your
probability.

Subtracting the maximum looks like it ought to change the answer, and it does not — that is the whole trick. The same
constant $c$ appears in every exponential on the top and on the bottom, so it factors straight back out:

$$
\frac{e^{z_j - c}}{\sum_k e^{z_k - c}} = \frac{e^{-c}\,e^{z_j}}{e^{-c}\sum_k e^{z_k}} = \frac{e^{z_j}}{\sum_k e^{z_k}}
$$

Any $c$ at all would cancel. Choosing $c = \max_k z_k$ is what makes it *useful*: the largest exponent becomes $e^{0} = 1$
and every other one is smaller, so no term can overflow. Without the shift, a logit of 800 — which a diverging run reaches
without much effort — sends ```std::exp``` to ```inf```, and ```inf / inf``` is ```NaN```. The loss becomes NaN, every
gradient computed from it becomes NaN, every weight becomes NaN, and the model is destroyed in a single step, silently.
Two lines of shifting buy immunity from that.

The code takes matrices as parameters. This is because we are working with batches — one row per sample, one column per
class — and each row is turned into its own distribution independently. Don't worry about this, we will work it through in
the later files. Two details in the signature are worth a look. It returns ```Matrix&``` and mutates its argument, so a
softmax over a batch allocates nothing at all; and it walks the row with ```base = i * cols```, the flat indexing from
```matrix.hpp```.

```cpp
inline Matrix& softmax(Matrix &M){
    const int rows = M.rows;
    const int cols = M.columns;
    
    for (int i = 0; i < rows; ++i){
        const int base = i * cols;                 // start of row i in flat storage

        // 1. row max (over the class columns) for stability
        double row_max = M.row_values[base];
        for (int j = 1; j < cols; ++j)
            row_max = std::max(row_max, M.row_values[base + j]);

        // 2. exp(x - row_max) and 3. accumulate the sum, in one sweep
        double sum = 0.0;
        for (int j = 0; j < cols; ++j){
            const double e = std::exp(M.row_values[base + j] - row_max);
            M.row_values[base + j] = e;
            sum += e;
        }

        // 4. normalise. Multiply by the reciprocal once instead of dividing per element.
        const double inv = 1.0 / sum;
        for (int j = 0; j < cols; ++j)
            M.row_values[base + j] *= inv;
    }
    return M;
}
```

The next two functions will be familiar. ```binary_cross_entropy_loss``` and ```cross_entropy_loss``` are the chosen loss
functions at the final layer. ```cross_entropy_loss``` collects loss across many mutually exclusive classes, as opposed to
```binary_cross_entropy_loss```, which only considers two. Written out as the code computes them, over a batch of $N$ rows
and $C$ columns:

$$
L_{\mathrm{CE}} = -\frac{1}{N}\sum_{i=1}^{N}\sum_{j=1}^{C} y_{ij}\log p_{ij}
$$

$$
L_{\mathrm{BCE}} = -\frac{1}{NC}\sum_{i=1}^{N}\sum_{j=1}^{C}
\Bigl[\,y_{ij}\log p_{ij} + (1 - y_{ij})\log(1 - p_{ij})\,\Bigr]
$$

Read those two denominators carefully, because they differ and the difference is deliberate. Cross-entropy treats each
**row** as a single categorical answer: the row is one probability distribution, exactly one class is correct, so a row
contributes one number and averaging over the batch means dividing by $N$. BCE treats each **cell** as its own independent
yes/no question — $C$ separate coin flips per sample, any number of which may be 1 — so the batch contains $NC$ answers
and it divides by $NC$. Take one function's formula and the other's normalisation and you are wrong by a factor of $C$,
which looks exactly like a badly chosen learning rate and is much harder to find.

Both clamp with ```eps = 1e-7``` before taking a logarithm, because $\log(0)$ is $-\infty$ and one confident, wrong
prediction would otherwise take the entire batch's loss to infinity. BCE clamps at both ends, into $[\varepsilon,\,
1 - \varepsilon]$, because it evaluates $\log(1 - p)$ as well as $\log(p)$ and can therefore be destroyed from either
side. CE only ever takes $\log(p)$, so a floor is all it needs.

Because the truth rows are one-hot, every term where y = 0 contributes 0 × log p = 0, and each sample's loss collapses to −log of the single ringed probability: the model is scored purely on how much belief it put on the right answer. The two per-sample losses are then averaged over the batch, which is the 1/N in the formula and the division by pred.rows in the code."

```cpp
inline double binary_cross_entropy_loss(const Matrix &pred, const Matrix &truth){
    if (pred.rows != truth.rows || pred.columns != truth.columns){
        throw std::invalid_argument("Prediction and truth matrices do not have the same dimensions");
    }
    
    const double eps = 1e-7;
    double loss = 0.0;

    for (std::size_t i = 0; i < pred.row_values.size(); ++i) {
        double p = std::min(std::max(pred.row_values[i], eps), 1.0 - eps);
        loss += truth.row_values[i] * std::log(p) + (1.0 - truth.row_values[i]) * std::log(1.0 - p);
    }
    
    return -loss / (static_cast<double>(pred.rows) * static_cast<double>(pred.columns));
}

inline double cross_entropy_loss(const Matrix &pred, const Matrix &truth){
    if (pred.rows != truth.rows || pred.columns != truth.columns){
        throw std::invalid_argument("Prediction and truth matrices do not have the same dimensions");
    }
    const double eps = 1e-7;
    double loss = 0.0;
    const int n = pred.rows;
    const int m = pred.columns;
    for (int i = 0; i < n; ++i) {
        for (int j = 0; j < m; ++j){
            const double p = std::max(pred.row_values[i * m + j], eps);   // guard log(0)
            loss += truth.row_values[i * m + j] * std::log(p);
        }
    }

    return -loss / static_cast<double>(n);
}
```

Next we look at the gradient function for ```cross_entropy_loss```. Observe that we use our in-place ```Matrix``` helper
```scale_```, as this avoids creating new ```Matrix``` objects unnecessarily. The important thing about this function is
what it differentiates with respect to: not the probabilities, but the **logits** — the pre-softmax scores.

$$
\frac{\partial L}{\partial z_{ij}} = \frac{p_{ij} - y_{ij}}{N}
$$

That is far simpler than it has any right to be. Getting there honestly means differentiating the loss back through the
softmax, and the softmax's Jacobian is not a pleasant object: every output depends on every input, because they all share
the one denominator. What happens is that the loss derivative $-y/p$ and that Jacobian cancel almost entirely, and all
that survives is $p - y$. It is one of the tidiest results in the subject, and it is exactly why softmax and cross-entropy
are always used as a pair: apart they are awkward, together their derivative is a subtraction. The same cancellation
happens for sigmoid paired with BCE, so this is a general pattern rather than a fluke of this one case — but note that
this function divides by $N$, matching ```cross_entropy_loss``` and *not* BCE's $NC$, so it is not a drop-in gradient for
the BCE above.

The $1/N$ is not optional, either. A loss that is averaged over the batch needs a gradient that is averaged over the batch
too, otherwise the size of every weight update quietly scales with however many samples happened to be in it.

```cpp
inline Matrix cross_entropy_loss_grad(const Matrix &pred, const Matrix &truth){
    if (pred.rows != truth.rows || pred.columns != truth.columns){
        throw std::invalid_argument("Prediction and truth matrices do not have the same dimensions");
    }
    Matrix grad = element_wise_subtract(pred, truth);   // PURE: fresh buffer, pred untouched
    scale_(grad, 1.0 / static_cast<double>(pred.rows)); // IN-PLACE: on our own buffer
    return grad;
}
```

Finally some wrappers that combine these functions — and they exist for a real reason, not for tidiness.

The output layer of the MLP hands back raw logits. Its activation is ```LINEAR```, and ```MLP.hpp``` refuses to be
constructed any other way. But ```cross_entropy_loss``` and ```cross_entropy_loss_grad``` both assume their ```pred```
argument is *already* a probability distribution — one takes the logarithm of it, the other returns the fused
$(p - y)/N$. Hand either one a matrix of logits and it will return a number, raise nothing, and be wrong. The wrappers
close that gap by running the softmax first, on a copy, since ```softmax``` mutates what it is given.

They are also a **matched pair** in the calculus sense: ```softmax_cross_entropy_loss_grad(z, y)``` genuinely is the
derivative of ```softmax_cross_entropy_loss(z, y)``` with respect to ```z```. That is precisely what a numerical gradient
check needs — nudge one logit, re-evaluate the loss, compare the finite difference against the analytic gradient — and it
is what ```grad_check.hpp``` gets handed for the first of its two checks, on a ```LINEAR``` layer.

```cpp
inline double softmax_cross_entropy_loss(const Matrix& logits, const Matrix& truth){
    Matrix probs = logits;   // copy: softmax mutates in place
    softmax(probs);
    return cross_entropy_loss(probs, truth);
}
inline Matrix softmax_cross_entropy_loss_grad(const Matrix& logits, const Matrix& truth){
    Matrix probs = logits;
    softmax(probs);
    return cross_entropy_loss_grad(probs, truth);
}
```

And lastly, an alternative loss function; mean squared error.

$$
L_{\mathrm{MSE}} = \frac{1}{N}\sum_{i=1}^{N}\sum_{j=1}^{C}\bigl(a_{ij} - y_{ij}\bigr)^{2}
\qquad
\frac{\partial L}{\partial a_{ij}} = \frac{2\,\bigl(a_{ij} - y_{ij}\bigr)}{N}
$$

Read that normalisation carefully too, because the name lies a little: the sum runs over every element, but the division
is by ```pred.rows``` alone. It is a *sum* over one sample's outputs and a *mean* over the batch — the same convention as
the cross-entropy above, chosen so that the two are interchangeable. Differentiate the textbook $\frac{1}{NC}\sum(a-y)^2$
instead and your answer will be a factor of $C$ away from what ```mse_loss_grad``` returns, and you will conclude the
gradient check is broken when it is the arithmetic that is.

The deeper difference is *what* the derivative is taken with respect to. ```mse_loss_grad``` returns
$\partial L / \partial a$: a plain derivative with respect to the network's output, with no activation folded into it.
```cross_entropy_loss_grad``` returns $\partial L / \partial z$, with the softmax already absorbed. That is why both are
here. An honest $\partial L / \partial a$ can be handed to a **nonlinear** output layer, which will then multiply by the
activation derivative itself on the way back — the ```tanh_deriv``` / ```relu_deriv``` path, and the Hadamard product that
applies it. Softmax and cross-entropy only ever exercise the ```LINEAR``` case, where that derivative is 1 and a bug in
that path stays invisible. That is exactly why the second gradient check is MSE against a ```TANH``` layer: between them
the two checks cover the code that neither pair could reach alone.

```cpp
inline double mse_loss(const Matrix &pred, const Matrix &truth){
    if (pred.rows != truth.rows || pred.columns != truth.columns){
        throw std::invalid_argument("Prediction and truth matrices do not have the same dimensions");
    }
    double sum = 0.0;
    for (std::size_t i = 0; i < pred.row_values.size(); ++i){
        const double diff = pred.row_values[i] - truth.row_values[i];
        sum += diff * diff;
    }
    return sum / static_cast<double>(pred.rows);
}
inline Matrix mse_loss_grad(const Matrix &pred, const Matrix &truth){
    if (pred.rows != truth.rows || pred.columns != truth.columns){
        throw std::invalid_argument("Prediction and truth matrices do not have the same dimensions");
    }
    Matrix grad = element_wise_subtract(pred, truth);              // (a - truth)
    scale_(grad, 2.0 / static_cast<double>(pred.rows));           // 2(a - truth)/N
    return grad;
}
```

That is the whole of ```math.hpp```: three activations with their derivatives, one softmax, four losses and their
gradients. Every one of them is a function of plain numbers or of a ```Matrix```, and none of them knows that a neural
network exists. The next file is where they start to be assembled into one — a layer is a weight matrix, a bias, and one
of these activations chosen from an enum.
