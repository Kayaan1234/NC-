## layer.hpp

Everything up to now has been ingredients. ```matrix.hpp``` gave us somewhere to put numbers and a handful of operations
to push them around with, and ```math.hpp``` gave us activations and losses that know nothing about neural networks at
all. This file is where the two finally meet, because a layer is a weight matrix, a bias row, one activation function,
and enough memory to remember what it did.

Imports, for completeness.

```cpp
#pragma once
#include <cmath>
#include <vector>
#include <algorithm>
#include <stdexcept>
#include "matrix.hpp"
#include <random>
#include "math.hpp"
```

Before the struct itself, we need a way of saying which activation a layer uses. We could store a function pointer
directly, but then a layer would have no idea what it was holding, and we would have no way of asking it for the matching
derivative later. An enum solves both.

```cpp
enum Activation{
    TANH,
    SIGMOID,
    RELU,
    LINEAR,   // identity: forward = x, f'(a) = 1. Used by the output layer,
              // whose softmax+CE gradient is handled in the loss instead.
};
```

```LINEAR``` is the odd one out, and it is worth knowing why it is here before we go any further. It means "do nothing",
so the layer hands its raw sums straight out. That sounds pointless right up until you remember the wrappers at the end
of the <LearnLink to="/training/step1/learn/math">math page</LearnLink>. Softmax and cross-entropy are a matched pair and
they want logits, so the layer that feeds them has to leave its numbers alone. ```LINEAR``` is how a layer says "the loss
function will take it from here".

Now the dispatch. We give ourselves an alias for "a function taking a ```double``` and returning a ```double```", and
then one function that turns an enum value into the real thing.

```cpp
// Map the activation enum to the scalar function that apply_/apply expects.
inline double identity(double x){ return x; }   // LINEAR (output layer)

using ActFn = double(*)(double);
inline ActFn activation_fn(Activation act){
    switch (act) {
        case TANH:    return tanh_act;
        case SIGMOID: return sigmoid;
        case RELU:    return relu;
        case LINEAR:  return identity;
    }
    throw std::invalid_argument("activation_fn: unknown Activation");  // also silences -Wreturn-type
}
```

That ```throw``` after the switch looks unreachable, and for a well behaved ```Activation``` it is. It is there because
the compiler cannot prove an enum only ever holds one of its four named values, so without it we get a warning about
control reaching the end of a non-void function. A throw is a cheap way to make the warning go away and be honest at the
same time.

Now the mirror image, which returns the derivative instead.

```cpp
inline double identity_deriv(double){ return 1.0; }  // LINEAR: f(x)=x => f'=1

inline ActFn activation_deriv_fn(Activation act){
    switch (act) {
        case TANH:    return tanh_deriv;
        case SIGMOID: return sigmoid_deriv;
        case RELU:    return relu_deriv;
        case LINEAR:  return identity_deriv;
    }
    throw std::invalid_argument("activation_deriv_fn: unknown Activation");  // silences -Wreturn-type
}
```

Two functions with the same shape, which is the point. The forward pass asks for $f$ and the backward pass asks for
$f'$, and both get it the same way from the same enum, so there is no chance of a layer applying tanh going forward and
sigmoid's derivative coming back. Note also that ```identity_deriv``` takes an unnamed parameter, because the answer is
1.0 whatever you pass it, and naming a parameter you never read is another warning waiting to happen.

Now the struct. Have a look at the attributes before anything else, because they explain the whole design.

```cpp
struct Layer{
    // parameters (these learn)
    Matrix weight;        // (fan_in x fan_out)
    Matrix bias;          // (1 x fan_out)

    // cache: written in forward, read in backward. Shapes depend on batch size,
    // so they start empty (default Matrix) and are assigned on the first forward.
    Matrix cache_input;
    Matrix cache_output;

    // gradients: filled by backward, consumed by update. Shapes known now, zeroed.
    Matrix grad_weight;   // (fan_in x fan_out)
    Matrix grad_bias;     // (1 x fan_out)

    Activation activation_type;
```

Six matrices, in three pairs, and each pair is there for a different reason.

```weight``` and ```bias``` are the parameters. They are the only things on the layer that learn, and their shapes are
fixed the moment the layer is built. ```fan_in``` is how many numbers come in per sample and ```fan_out``` is how many go
out, so the weight matrix is ```fan_in``` by ```fan_out``` and the bias is a single row of ```fan_out```, exactly the
shape that broadcast add from ```matrix.hpp``` was written for.

```grad_weight``` and ```grad_bias``` are where the backward pass puts its answers. Their shapes match the parameters
they belong to, which is not a coincidence and is worth holding onto, because it is the single most useful sanity check
you have when a backward pass goes wrong.

```cache_input``` and ```cache_output``` are the interesting pair. The backward pass needs to know what the layer saw and
what it produced, and neither of those is known until someone actually calls ```forward```. Their shapes depend on the
batch size, which the layer is not told when it is constructed, so they start life as empty default matrices.

The constructor follows straight on.

```cpp
    Layer(int fan_in, int fan_out, Activation activation, std::mt19937& rng)
        : weight(fan_in, fan_out, rng),
          bias(1, fan_out),
          grad_weight(fan_in, fan_out),
          grad_bias(1, fan_out),
          activation_type(activation) {
    }
```

Four of our overloaded ```Matrix``` constructors, all in one initialiser list. ```weight``` gets the one that takes an
```std::mt19937&``` and fills itself from a gaussian scaled by $1/\sqrt{\texttt{rows}}$, which is the same trick the
single neuron used to keep its sums in the steep part of the activation. Everything else gets the zero-filled shape
constructor. Biases start at zero on purpose, because there is nothing to break symmetry between: two units with the same
bias but different weights are already different units.

Now the forward pass, which is three lines of real work.

```cpp
    const Matrix& forward(const Matrix &input) {
        const int batch   = input.rows;
        const int fan_out = weight.columns;

        // (Re)allocate the output buffer only when the batch shape changes -- i.e.
        // once for a fixed batch size. Also mandatory for correctness: matmul's
        // out-buffer overload writes into existing storage and never resizes.
        if (cache_output.rows != batch || cache_output.columns != fan_out)
            cache_output = Matrix(batch, fan_out);

        matmul(input, weight, cache_output);                  // z -> owned buffer
        element_wise_add_(cache_output, bias);                // + bias, in place
        apply_(cache_output, activation_fn(activation_type)); // -> a, in place

        cache_input = input;        // backward needs the input it saw
        return cache_output;        // by reference: the next layer reads it directly
    }
```

In maths, that is

$$
z = XW + b
\qquad
a = f(z)
$$

and the shapes are what make it work. $X$ is ```batch``` by ```fan_in```, $W$ is ```fan_in``` by ```fan_out```, so $XW$
comes out ```batch``` by ```fan_out```, and the bias row of ```fan_out``` broadcasts down every row of it.

That ```if``` at the top is doing two jobs. The obvious one is that we avoid reallocating a buffer we already have, which
is the whole reason ```matmul``` has an out-buffer overload in the first place. The less obvious one is that we have to,
because that overload writes into storage that already exists and will never resize it for us. Train with a fixed batch
size and this branch is taken exactly once.

The last two lines are quiet but they matter. ```cache_input = input``` takes a copy of the whole batch, because the
backward pass will need it and the caller is under no obligation to keep it around. Then we return by reference, so the
next layer along reads this layer's output directly out of this layer's own buffer with nothing copied in between.

Now the backward pass, which is the hardest thing in the file and honestly the hardest thing in Step1. Take it slowly. A
gradient comes in from the layer in front, and three gradients have to come out.

```cpp
    Matrix backward(const Matrix &upstream_gradient){ //this is dL/da
        int batch = upstream_gradient.rows;
        int fan_out = upstream_gradient.columns;

        Matrix temp = apply(cache_output,activation_deriv_fn(activation_type)); //da/dz
        hadamard_(temp, upstream_gradient); // dL/dz, as activation was applied across every value
```

The thing arriving is $\partial L/\partial a$, the gradient of the loss with respect to what this layer output. The first
job is to get back past the activation to $\partial L/\partial z$, the gradient with respect to the sums before the
activation ran. Chain rule:

$$
\frac{\partial L}{\partial z} = \frac{\partial L}{\partial a} \odot f'(a)
$$

and there is our friend the Hadamard product, doing exactly the job it exists for. The activation was applied to every
cell independently, so its derivative comes back cell by cell too, with no summing anywhere. This is also where the
convention from ```math.hpp``` pays for itself. We pass ```cache_output``` into ```activation_deriv_fn```, which is $a$,
the value that came out, so nothing gets recomputed.

Next, the bias.

```cpp
        std::vector<double> grad_bias_vec(fan_out, 0.0);   // pre-allocate, zero-init

        for (int i = 0; i < batch; ++i) {
            for (int j = 0; j < fan_out; ++j) {
                grad_bias_vec[j] += temp.row_values[i * fan_out + j];
            }
        }
        
        grad_bias = Matrix(1,fan_out,grad_bias_vec);
```

$$
\frac{\partial L}{\partial b_j} = \sum_{i=1}^{N} \frac{\partial L}{\partial z_{ij}}
$$

We add up a whole column and get one number. The reason is broadcasting. On the way forward, one bias value was added to
every row of the batch, so it had a hand in every one of those rows, and the chain rule says a parameter used $N$ times
collects the gradient from all $N$ uses. Every time you see a broadcast on the way forward, expect a sum on the way back.

Then the weights, and here we get to use ```transpose```.

```cpp
        //need dL/dW. Output has shape (batch, fan_out), W has shape (fan_in, fan_out)

        grad_weight = matmul(transpose(cache_input), temp);
```

$$
\frac{\partial L}{\partial W} = X^{\mathsf{T}} \frac{\partial L}{\partial z}
$$

If the transpose looks like it came out of nowhere, do the shapes. $X$ is ```batch``` by ```fan_in```, so $X^{\mathsf{T}}$
is ```fan_in``` by ```batch```, and multiplying that by a ```batch``` by ```fan_out``` gradient gives ```fan_in``` by
```fan_out```. That is the shape of ```weight```, which is the only shape the answer could possibly have been. Whenever
you cannot remember where a transpose goes in backprop, put it wherever the shapes come out right and you will be
correct.

And last, the gradient we hand backwards.

```cpp
        //finally dL/dX - this is just dL_dz x dz_dX. dz_dX is W^T. 
        return matmul(temp, transpose(weight));
    }
```

$$
\frac{\partial L}{\partial X} = \frac{\partial L}{\partial z} W^{\mathsf{T}}
$$

Same trick with the shapes. ```batch``` by ```fan_out``` times ```fan_out``` by ```fan_in``` gives ```batch``` by
```fan_in```, which is the shape of this layer's input and therefore the shape of the previous layer's output. That is
what makes a stack of these things chain together: what one layer returns is exactly what the layer behind it expects to
receive.

Finally, ```update```, which is where learning actually happens.

```cpp
    Matrix& update(double lr){
        scale_(grad_weight, lr);
        scale_(grad_bias, lr);

        element_wise_subtract_(weight, grad_weight);
        element_wise_subtract_(bias, grad_bias);

        return weight;
    }
};
```

$$
W \leftarrow W - \eta \frac{\partial L}{\partial W}
\qquad
b \leftarrow b - \eta \frac{\partial L}{\partial b}
$$

Gradient descent, the same as the single neuron did it, only now with matrices doing the work. Both helpers are the
in-place versions with the trailing underscore, so the whole update runs without allocating anything.

One thing to be aware of, since it surprised me. ```scale_(grad_weight, lr)``` multiplies the stored gradient by the
learning rate in place, so after ```update``` runs, ```grad_weight``` no longer holds a gradient. It holds a gradient
times $\eta$. That is completely safe here, because the very next ```backward``` assigns a brand new matrix over the top
of it before anybody reads it again. It is safe because of the order the calls happen in, so it is worth remembering if
you ever want to look at a gradient after an update, or add anything like momentum that expects to find the real
gradient still sitting there.

That closes the ```Layer``` struct and the file. Four things live here: an enum that names an activation, two dispatch
functions that turn that name into $f$ and $f'$, and a struct that runs one layer forward, backward and one step downhill.
Next we stack them.
